## 1. Data source

`nolhc_ml/data/raw/nolhc_runs.xlsx` (`ExpValues` / `SimResults` sheets) — the same raw file the production 129-run benchmark was built from. Loaded, cleaned (3-row grouped header flattened), and verified: **129 rows, 35 real inputs, 20 real outputs, zero missing values** — matches every other document in this repo that quotes 129×35×20.

## 2. KPI selection (3 of 20) and why

The spec asks for KPIs "grounded in real data," not an arbitrary pick. I chose three that span the engine's actual model-family mix, using `experimenting_ml/docs/CV_Best_Models_Per_Target.md` as the source of which model won each KPI:

| KPI | CV-selected model | CV RMSE | Why chosen |
|---|---|---|---|
| `TT_OB_Agri` | ExtraTrees | 7.30 | Tree-family winner — tests whether a GP ground truth is a fair stand-in for a KPI whose *real* surrogate is a tree ensemble |
| `TT_IB_LB` | GPR (Matérn) | 21.49 | The engine's hardest, most decision-relevant KPI (wide conformal interval, the congestion-threshold behaviour discussed in the manuscript) — already GP-shaped in production |
| `Uti_DAFM_R` | GPR (Matérn) | 0.0104 | The engine's easiest, best-behaved KPI — a sanity-check floor |

This deliberately covers one tree-won and two GPR-won KPIs, so the "does a GP make a fair ground truth?" question gets tested against both a favourable and an unfavourable case, not just favourable ones.

**Cross-check worth flagging:** the manuscript's Table 4 reports `TT_IB_LB` as Stacking-won (CV RMSE 21.214) rather than GPR_Matern (21.4914) from `CV_Best_Models_Per_Target.md`. Close numbers, different named winner — almost certainly a different pipeline snapshot (same pattern as the registry 4-vs-5 discrepancy Nila already flagged). I used `CV_Best_Models_Per_Target.md` throughout since it's the one file that covers all 20 KPIs from a single consistent run. Worth reconciling snapshots at some point, not blocking here.

## 3. Ground-truth surface: GP per KPI, fit on all 129 rows

Per spec §5.2: fit a GP per KPI on the full 129×35 sample. Implementation choices, and why they match the rest of the codebase rather than introducing new conventions:

- **Isotropic Matérn(ν=1.5) kernel**, single length-scale across all 35 (standardised) inputs — not ARD (per-dimension length-scales). ARD would try to fit 35 length-scale parameters from 129 points and is not identifiable at that ratio. This mirrors the manuscript's own §4.2 methodology, which also uses a single scalar length-scale, not ARD.
- **Inputs standardised** (`StandardScaler`), consistent with how the project already treats GPR/SVR/linear models (`ML_Pipeline_Specification.md`: tree models get raw inputs, everything else gets scaled).
- **Fit on all 129 rows**, not an 80/20 split. This surface's job is to *be* the simulator stand-in, not to generalise to unseen data in the usual sense — using every real point available maximises fidelity to the actual response.
- A `WhiteKernel` noise floor (bounds `1e-3` to `1e1`) is included in the fitted kernel itself, so the GP doesn't degenerate into pure memorisation of the 129 points (an earlier fit without a noise floor showed exactly that failure mode — see §5).

## 4. Noise model — and an honest limitation

Task 1's Theme 6 already flagged this: each of the 129 points was run with 5 DES replications and reported as a mean, but the per-replication values aren't retained anywhere in this repo — only the mean survives. **That means true DES replication variance cannot be measured from the data available.** I'm not going to pretend otherwise.

What I used instead, as a documented assumption (not a measured quantity):

```
injected_noise_std(KPI) = 0.15 × CV_RMSE(KPI)
```

CV RMSE is a real, reported number per KPI (`CV_Best_Models_Per_Target.md`), so the noise scale is grounded in something real rather than picked from thin air — but it conflates metamodel error with true output variability, it is **not** a measurement of replication noise specifically. The 0.15 fraction is a placeholder I chose to keep injected noise small relative to typical prediction error, not a fitted or derived value.

**Before this goes in the report:** either accept this as an explicitly-labelled assumption (recommended for a v0 deadline-constrained deliverable), or ask the mentor/simulation partner whether raw per-replication AnyLogic output can be exported — that would let this be a real, measured intrinsic-noise estimate instead. Flagging as a decision, not deciding it myself.

## 5. Validation — and one finding that needs a team decision

I ran a 5-fold CV on the GP surface itself (the ground-truth model, not the production model) to check how well "GP as universal ground truth" actually holds up:

| KPI | Production model's own CV RMSE | GP-ground-truth 5-fold CV RMSE | Verdict |
|---|---|---|---|
| `TT_IB_LB` | 21.49 (GPR_Matern) | 21.56 | **Matches closely** — expected, since the real winner is already a GP |
| `Uti_DAFM_R` | 0.0104 (GPR_Matern) | 0.0109 | **Matches closely** — same reason |
| `TT_OB_Agri` | 7.30 (ExtraTrees) | 22.43 | **~3× worse** |

The GP ground truth is a good stand-in for `TT_IB_LB` and `Uti_DAFM_R` — unsurprising, since both are already won by a GP in production, so we're not asking the surrogate to do anything unfamiliar. For `TT_OB_Agri`, forcing a smooth isotropic GP onto a response surface that a tree ensemble models 3× better is a real, measured weakness, not a hypothetical one.

**Recommendation:** for KPIs where the real winner is a tree model, use the already-trained production model (`experimenting_ml/outputs/trained_models/*.joblib`) as the ground-truth stand-in instead of forcing a GP, and reserve the GP-fitting approach for GPR-won KPIs. This is a deviation from the spec's stated "primary approach: fit a GP per KPI" — flagging it as a recommendation for team sign-off, not something I changed unilaterally. I can implement the tree-model-as-ground-truth swap for `TT_OB_Agri` in about ten minutes if the team wants it before T2.5 locks in.

## 6. What T2.5 (Nila) gets from this

Two files, both attached, both runnable as-is:

- `loop/des_backend/ground_truth_gps.joblib` — fitted scaler + 3 GPs + noise stds, loadable directly.
- `loop/des_backend/synthetic_backend.py` — a `SyntheticGroundTruth` class with a `.run(x_row, kpi, n_replications, seed)` method: returns GP posterior mean, GP epistemic std, and `n_replications` noisy synthetic "DES runs." This is meant to be imported as-is or adapted into `SyntheticDESBackend` (spec §5.4) — the interface already matches what a DES backend needs to expose (mean, uncertainty, noisy replications).

Demo output (run via `python synthetic_backend.py`) confirms the sanity behaviour T2.4's novelty scorer will depend on: an in-sample candidate gets `gp_std ≈ 17.3`; the same candidate with one input pushed to 3× its observed maximum gets `gp_std ≈ 134.1` — GP epistemic uncertainty correctly balloons outside the training hull, which is exactly the signal T2.4 needs to build on.

## 7. Open item carried to T2.4

The novelty/OOD scorer (T2.4) can use this GP's own `gp_std` as one novelty signal for free — no extra work — alongside whatever Mahalanobis/isolation-forest distance metric Theme 5 of the SOTA review recommends. Worth deciding whether T2.4 uses GP-std, hull-distance, or both; I'd lean toward both, cross-checked against each other, since they can disagree in informative ways (e.g. a point could be geometrically inside the convex hull but still far from any actual training point in a sparse region).
